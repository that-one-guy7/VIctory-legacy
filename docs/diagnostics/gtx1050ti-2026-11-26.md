# GTX 1050 Ti run — 2026-11-26

This is a compact, text-only summary of the machine log shared for this run. The raw
`ztrx.log` is intentionally not tracked: it is machine-specific, larger than the
repository's 512 KiB text-file limit, and is ignored by `.gitignore`.

## Environment

- Windows 10 build 19044, Intel Core i7-6700 (8 logical processors), 16 GiB RAM.
- NVIDIA GeForce GTX 1050 Ti, 4 GiB reported adapter memory; driver 32.0.15.8278.
- The launcher used the **release** profile, not the diagnostics profile.
- DXGI local-memory budget varied around 3,345–3,403 MiB.

## Confirmed rendering problems

- The title requested a 1,245,184-entry view heap. The NVIDIA host heap probe failed
  above 1,000,000 entries, so indices beyond the host's retained range are mapped
  to a null descriptor. The log did not report dynamic descriptor-slot exhaustion.
- Shader translation refused compute shader `a929109552ce1e84` because
  `v_permlanex16_b32` was unsupported.
- Shader translation refused compute shader `f133e35efed2a48a` because a lane-mask
  exchange occurred where not every lane runs.
- Shader translation refused compute shader `ceb5eb68cd99cb07` because descriptor
  address/format bits were read as data.
- Pixel shaders `7d0f14ce44746d7e` and `6b6db9f1a526daeb` also read descriptor
  data in a form the older translator refused.
- Pipeline backlogs stayed large: sampled frame diagnostics showed roughly
  1,400–2,200 pipelines still being made. Later frame summaries reported hundreds
  to thousands of dropped draws/dispatches waiting for host pipelines.

## Device-removal evidence

- Optional local UAV allocations were refused near the normal 85% DXGI
  budget threshold. The log shows a 510 MiB local mesh-scratch pool (15% of
  the 3,403 MiB budget), with about 109 MiB in it at a later checkpoint.
- The low-VRAM launcher profile was not active in this run: the log shows 10
  card-side title-buffer copies totalling 492 MiB, while that profile sets
  `VICTORY_CARD_BUFFERS=0` and caps local mesh scratch at 128 MiB. It also
  lowers the optional-UAV threshold to 70%. The profile is opt-in through
  `VICTORY_MESH_FALLBACK=1`.
- Despite the normal optional-allocation guard and mesh-scratch fallback,
  local usage later reached about 4,029 MiB against a 3,403 MiB budget.
- The device was removed after a submission of 22 command lists. The log reported
  `0x887A0005` and `0x887A0004`, but no DRED breadcrumbs or page-fault details.
- Because this was a release run without DRED, the exact offending command/resource
  cannot be identified from this log alone. Device removal is confirmed; a single
  root cause is not.

## Existing texture-budget behavior and remaining gap

The existing `resource::room()` check is already used by the dedicated
`heap_textures()` pass for textures picked by index. When the local budget is
full, that pass leaves those slots due for a later retry. The log shows the
indexed-texture queue was large (27,526 slots at one checkpoint), but the host
had only 492 MiB of its own indexed-texture copies and continued deferring
some optional UAV allocations. This is not enough evidence to conclude that
indexed texture copies alone caused the later 4,029 MiB local usage.

Ordinary host textures, render targets, depth twins, and required UAV/indirect
buffers have different lifetime and correctness requirements. A blanket
admission check on every texture object would also defer normal sampled
textures beyond the indexed-texture path, so it is deliberately not added
without better evidence. The exact allocation class responsible for the
over-budget usage remains unproven.

## Follow-up

The renderer PR ports the confirmed permlane and descriptor-size translator
cases and raises the default pipeline worker count from four to five on this
eight-logical-processor machine. The divergent lane-mask exchange remains
unsupported pending a safe cross-wave implementation. The next hardware run
must use a diagnostics build with `VICTORY_D3D12_DRED=1` so command breadcrumbs
and page-fault data can identify the exact resource or command list that
causes device removal.
